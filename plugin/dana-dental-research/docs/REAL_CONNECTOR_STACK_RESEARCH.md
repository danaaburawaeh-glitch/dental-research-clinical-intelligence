## Other categories addressed by name

- **Journal publisher APIs (direct):** Not investigated per-publisher in this pass — this is a large, fragmented landscape (Elsevier, Wiley, Springer each with separate developer programs, subscription-gated, differing terms). Recommend treating `~~journal-access` as continuing to route through Crossref (metadata + DOI resolution) plus OpenAlex (open-access full-text links via its Unpaywall integration) rather than building direct per-publisher integrations, unless a specific publisher relationship already exists. Full per-publisher survey would need its own research pass if you want it.
- **Manufacturer IFU retrieval:** No general-purpose API exists for this by nature — IFUs are published per-manufacturer, often as static PDFs on individual company sites, with no standardized registry or search API found or expected. `~~manufacturer-ifu`'s realistic fallback (user-supplied IFU excerpt, tagged USER-SUPPLIED, per the existing connector map) remains the correct model; this was not something a further search was likely to change, so no additional query was spent here.

## Cross-cutting notes for CONNECTOR_REQUIREMENTS.md (Phase 16)

1. **OpenAlex's Feb-2026 API-key requirement** is a breaking change relative to what a lot of
   still-circulating tutorials/docs describe (mailto-only polite pool). Any Phase 16
   `CONNECTOR_REQUIREMENTS.md` entry for OpenAlex should specify the key requirement explicitly so
   it isn't built against stale documentation.
2. **Crossref's rate limits were tightened 1 Dec 2025** (public pool now 5 req/s / concurrency 1;
   polite pool 10 req/s / concurrency 5) — noticeably lower than older "50 req/s" figures that
   still appear in some third-party docs. Build against the current, lower numbers.
3. **Semantic Scholar's exact current unauthenticated rate limit is inconsistently documented**
   across sources found this session (figures from "1 req/s" to "5,000/5min" to "1000 req/s shared"
   appear across different pages). This should be verified directly against the official API
   overview page at build time rather than hard-coded from this research pass.
4. **SFDA has a real open-data API** — this is the most consequential finding for M4/regulatory
   work specifically, though M4 is out of scope for this v0.3 release. Recording it here now so
   it isn't lost before M4 migration begins.
5. No MCP servers were found this session for Crossref, OpenAlex, ClinicalTrials.gov, Cochrane, or
   SFDA specifically — PubMed and Semantic Scholar are the only two source categories with existing
   third-party MCP servers. Everything else would need a purpose-built MCP wrapper if you want
   MCP-level integration rather than direct API calls from within skill logic.
